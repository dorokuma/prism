> Version: v0.38.2  Date: 2026-10-09  Status: living document

## Quick start (local)

```bash
git clone <repo>
cd prism
go build -o prism ./cmd/prism
cp config.yaml.example config.yaml
# set keys (pick one):
#   export PRISM_KEY_ACCOUNT_1=... PRISM_KEY_ACCOUNT_2=...
#   or put key: in config.yaml (local only, never commit)
./prism
```

Default listen: `127.0.0.1:18790` if unset. Prefer `127.0.0.1:18790` in production.

| Unit | `/etc/systemd/system/prism.service` (see `scripts/prism.service.example`) |

Source tree (`/root/prism` or the git clone) is for build only — **no production `config.yaml` / `.env`**.

### Account keys

For each account `name` (e.g. `go-plan-1`), if `key` is empty in YAML the process loads:

1. **systemd LoadCredential** file named `PRISM_KEY_GO_PLAN_1` under `$CREDENTIALS_DIRECTORY`
2. else environment **`PRISM_KEY_GO_PLAN_1`**

Hyphens in the account name become underscores in the credential/env name.

### Deploy / update binary

```bash
cd /path/to/prism
./deploy.sh   # HEALTH_URL / HEALTH_TIMEOUT are overridable; defaults below
```

`deploy.sh` builds, atomically replaces the binary, runs `systemctl restart prism`, health-checks, and rolls back automatically on failure.

- `HEALTH_URL`: health-check URL, default `http://127.0.0.1:18790/ready` (override for a non-default port or remote probe; older deploys can point it back at `/health`). The default is `/ready` (readiness: 200 only when at least one account is healthy and not in cooldown), not `/health` (liveness: 200 as soon as the process is up, which cannot detect an all-accounts-down deploy). `/ready` is a **fail-closed deploy gate**: when every account is in cooldown/exhausted (bad upstream key, upstream outage) the health check fails and the deploy rolls back — by design, so a build that corrupts account state must not ship. For liveness-only gating set `HEALTH_URL=http://127.0.0.1:18790/health` explicitly. If `HEALTH_URL` ends in `/ready` and the old process is already failing this round (not up, or the pool was already not ready), this round probes `/health` on the same host so an already-down upstream is not treated as a new-binary failure, rolled back, and restarted a second time.
- `HEALTH_TIMEOUT`: health wait window in seconds, default `35`, must be a positive integer (invalid values `exit 3` before any side effects; prism is untouched). After restart, poll `systemctl is-active` + `HEALTH_URL` every 1s; continue on the first success, roll back only when the window expires; the post-rollback check uses the same poll. The process listens first: `/health` is immediately 200, `/ready` stays fail-closed. The window waits for at least one successful account probe, not for Listen (per-account `ProbeTimeout` is 30s max). **Do not** stretch `HEALTH_TIMEOUT` to minutes hoping every account recovers — that only delays a rollback that is already determined; roll back and inspect (`journalctl -u prism`).
- `HEALTH_CURL_MAX_TIME`: per-probe `curl --max-time` in seconds, default `5`, must be a positive integer (invalid values also `exit 3` before side effects). The actual timeout is `min(HEALTH_CURL_MAX_TIME, HEALTH_TIMEOUT)` so one curl cannot outlast the whole window.

Manual deploy:

```bash
cd /path/to/prism
go build -o prism ./cmd/prism
install -m 755 prism /usr/local/bin/prism
# config edits: edit /var/lib/prism/config.yaml then:
systemctl restart prism   # only when you intend downtime / reload
# or: systemctl kill -s HUP prism   # if process supports SIGHUP for partial reload
```

### Tool config sync (`models.json`) ownership

`prism` rewrites pi's `~/.pi/agent/models.json` after every model refresh
(startup fill, 24h stale refresh, SIGHUP). The write is atomic (temp file +
rename) and preserves the deployed file's mode and owner/group via `chown`
on the temp file. Two consequences for installation:

- `models.json` should be owned by the prism service user (or its group,
  with group-write permissions), OR prism must be allowed to preserve the
  existing owner (the process needs root / `CAP_CHOWN` for that).
- If the owner cannot be preserved — e.g. `EPERM` under `NoNewPrivileges`
  with an empty `CapabilityBoundingSet` — the sync ABORTS with an error:
  it never renames a differently-owned file over the deployed one and
  never falls back to a non-atomic in-place overwrite. The old file stays
  byte-for-byte intact (same inode, owner, mode) and the failure is
  visible in the logs, so the ownership misconfiguration is surfaced
  instead of silently degrading.

`prism setup` normalizes an existing tool config at install time: owner →
the `prism` service user, group → `pi-sync` when that group exists
(otherwise kept), mode → at least `0664` (missing bits added, none
removed). A file that does not exist yet is left alone — the first sync
creates it as the prism process (temp file + rename), so its owner is the
service user by construction. Setup grants no capability anywhere (the
unit's `CapabilityBoundingSet` stays empty — `CAP_CHOWN` is deliberately
never granted; see `scripts/prism.service.example`). If the normalization
cannot be applied (e.g. the `prism` user is missing, or `chown` is
denied), setup fails with an explicit error.

| `usage` | map | disabled | Token usage recording to SQLite: `enabled` (default false, opt-in), `db_path` (default `/var/lib/prism/usage.db`; NOT hot-reloadable), `retention_days` (absent → default 30; explicit `0` → keep forever, cleanup disabled), `channel_size` (default 4096), `batch_size` (default 50), `batch_flush_ms` (default 200), `default_key_id` (default `anonymous`; key_id recorded for requests without an authenticated api key — explicit empty falls back to `anonymous`). The pricing basis follows the upstream wire format (OpenAI `prompt_tokens` includes cached tokens, Anthropic `input_tokens` excludes the cache counters) and is persisted per row as `usage_source`. ### Model remapping behavior

`model_remap` maps virtual model names to tiers. `model_tiers` maps each tier to an
upstream model name. The resolution logic is:

1. If the requested model is **in `model_remap`**:
   - Look up its tier, then look up that tier in `model_tiers`.
   - If both mappings exist → use the upstream model.
   - If the tier has no upstream mapping → fall back to `default_tier` (if set).
2. If the requested model is **not in `model_remap`**: pass through unchanged.
   (Real upstream model names are sent directly to the provider.)

> **Note:** Previously, all unknown models went through `default_tier`. The current
> behavior only applies `default_tier` to models that exist in `model_remap` but
> whose target tier has no upstream mapping.
| `mcp_tools_json` | string | — | Optional path to tool-definitions JSON. Cached MCP tools are bounded per API-key identity (100 tools) AND per single tool (1 MiB serialized: an oversized tool is dropped, never truncated, never logged in full) |
| `model_metadata` | map | — | Per-model metadata returned by /v1/models: context_window, max_tokens, reasoning, input, cost, thinking_level_map, extra. `cost` unit is USD per 1M tokens (e.g. `input: 0.6` = $0.6 per 1M input tokens). An optional `long_context` tier with `long_context_threshold` applies to prompt/input tokens when `tokens >= threshold`; completion tokens do not affect tier selection. |

The ClinePass windows additionally show the inferred `总额` (词元) — the account's `cline-pass/` consumption in each window (`in + out` per line, `cache_read` excluded to match the upstream percent's 口径) ÷ its used share, read strictly read-only from magpie's per-call log (`/root/.config/magpie/usage.jsonl`, streamed line by line, never held open); the source re-stats the log on every sum and rescans it only when the file version (device+inode / size / mtime) changed or the installed roster's key-tail table changed (a discovery that rotates a key, or one that does not confirm the table, invalidates the cached index even though the log did not move), so one scan answers every account and every window and an appended, truncated or replaced log is picked up on the next refresh with no restart; an unterminated last line (magpie appending while we read) is tolerated while a terminated line whose shape drifted (a `t` that is not RFC3339, missing `in`/`out`/`provider`/`model`) degrades that round to no total instead of silently mis-bounding the window; a missing or unreadable log, or one with no usable line, simply omits the total and never fails the fetch; source degradation is counted in `clinepass_usage_source_errors` (current state in `clinepass_usage_source_status`) on `/metrics` and logged once per state transition (WARN degraded / Info recovered, never once per round). ClinePass accounts and keys come from magpie's provider file (`/root/.config/magpie/providers.json`, the `clinepass` entry's `key` + `keys[]`; magpie's provider file carries no human label for a key, so an account is named `<provider id>#<providerKeyId>`); each account is polled with its own provider key and its consumption is summed per magpie's `providerKeyId` (the hex of the first 10 characters of SHA-256 of the key), so one account's traffic never inflates another's total. A share of the SAME account's traffic is written by magpie on lines it could not attribute to a key at all (no `providerKeyId`, a masked account label ``API key …326d`` instead; 921 such `cline-pass/` lines measured 2026-10-07) and those lines are counted too: the label's last four characters are matched against the roster's own key tails (`providerAccount`, falling back to the `host` field), and the row joins an account only on a UNIQUE match — a label no account's tail matches stays out of every account (the total is then a lower bound), and two accounts whose keys end in the same four characters disable the match entirely instead of attributing one subscription's traffic to the other (串账), WARNed once per transition. The model gate is unchanged and applies to both paths: only a `cline-pass/<model>` line counts, so magpie's free tier (`cline-free/*`) stays out either way. The roster is (re)discovered at startup and on every SIGHUP (a discovery error keeps the previous roster; a successful discovery — including one whose file names no ClinePass account — installs its own table), so an account added or removed while prism runs needs one SIGHUP; one FETCH takes that tail table once, at its start, and attributes all three of its windows through it (the 5-hour, weekly and monthly sums of one fetch share one table and one freshness verdict), so a SIGHUP landing between two windows cannot split one fetch between two rosters; a host WITHOUT a magpie provider file reports no accounts and no error and stays silent, so one SIGHUP during a swap/rollback window while the file is momentarily absent drops the ClinePass roster (restore the file, then send another SIGHUP). What such a discovery never leaves behind is a USABLE tail table: a discovery that did NOT read the provider file — it failed, or there was none — marks the installed table STALE, and a stale (or empty, or colliding) table attributes nothing, so every keyless row then falls through to the unattributed count until a discovery succeeds again. A keyless row must never be placed by a table prism could not re-confirm: the file it could not read is exactly the one magpie rewrites when it rotates a key, so a new key whose last four characters happen to equal a roster key's tail would otherwise credit the row to the wrong account (串账). The suspension is itself observable: `clinepass_usage_attribution_stale_total` counts the SUMS that ran without a confirmed table (one per window per account per round) — but only from the moment a table HAD been confirmed: a source that never confirmed one is not counted at all, since nothing was lost there and a per-sum tick would grow forever on a host without magpie while the WARN asked for a roster that was never installed. One WARN per transition names the reason, and the recovery line is logged by the successful discovery, never by a sum. Because magpie's log only reaches back to when magpie started recording (it is appended forever, never rotated and never backfilled), a window that STARTED before the log's first line can only be summed to a LOWER BOUND — the 总额 shown for it is too small (the monthly figure, derived as twice the weekly pool, is too small with it). That is a transitional state and heals by itself as each window rolls past the log's start; it is not silent either: `clinepass_usage_window_lower_bound_total` counts the sums in that shape and one WARN per window start names both the window's start and the log's start. The sibling silent zero — an account id that matches NO row in the log at all (magpie's `providerKeyId` derivation drifted, or the provider key was rotated so the id prism now derives has no rows of its own) — still yields no total and is counted in `clinepass_usage_account_unmatched_total`, with one WARN per account transition and one Info when the id matches rows again; neither counter moves `clinepass_usage_source_status`, which keeps its meaning of "the log could not be read". The keyless rows that fall out of attribution are counted separately, one per ROW per scan, in `clinepass_usage_unattributed_rows_total` (keyless `cline` rows of a `cline-pass/` model that matched no roster key tail) — a per-ROW unit, unlike `clinepass_usage_account_unmatched_total`, which is per ACCOUNT and only says that account's id matched no line at all. Read that row counter as a FLAG and never as a rate: its increment is per falling-through row per SCAN and a scan is the WHOLE file, so an appended line re-counts every falling-through row the log still holds (measured: +3 on a 3-falling-through-row fixture after a single append) while an unchanged file adds nothing at all, and a key-tail collision that holds every keyless row out makes it climb by roughly the whole keyless share each round (≈+921 measured) — a slope there is the re-scan, not new traffic, so do not set alert thresholds on its growth. A window at/above 100 % (or `used up` / `rate-limited`) reports its measured consumption as BOTH sides of the total (`X/X`, also exposed as `measured_tokens`) instead of a reversed pool. Independent of `usage.enabled`. Same `PRISM_ADMIN_TOKEN` auth as `/admin/usage/summary`. `format=table` for the CLI-style text report. Returns 503 `quota_unavailable` when `quota.enabled` is false. CLI: `prism quota` |

### Model Cache CLI

Manage and query upstream model caches directly or via HTTP:

```bash
# Query cache status via HTTP GET (read-only, does not trigger refresh)
prism models status

# Refresh all providers via HTTP API (default)
prism models refresh

# Refresh specific provider
prism models refresh --provider opencode-go

# Refresh in direct mode (writes to /var/lib/prism/model_cache directly, does NOT notify running prism instances; use ONLY when service is not running)
prism models refresh --direct --config /var/lib/prism/config.yaml

# Output machine-readable JSON
prism models refresh --json
```
