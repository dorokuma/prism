# 词元紧凑格式补齐 B/T/P/E 进位链：渲染值先按单位精度取整，取整到 1000 即进位

## 一句话结论
- `render.FormatTokens`（internal/render/numbers.go）在原有 k/M 之上补齐 B → T → P → E 进位链：先按“最大的、使缩放值 ≥ 1 的单位”渲染，若该精度的渲染结果 ≥ 1000（含四舍五入到 1000 的情形，如 999.96M → `1B`）则升一个单位重新渲染，直到缩放值 < 1000；M 段原有的 2 位/1 位小数分界（≤100M 用 2 位，>100M 用 1 位）逐字节保持不变。
- 仅改人类可读渲染；JSON/接口原始数值、字段名零改动。
- 卡片消费路径（`planusage.totalPart` → `已用 34% / 总额 4.6B 词元`）新增断言；`usage` 表格的 `reqWidth/cacheWidth = 6` 仍成立（进位后最长仍是 6 列：`999.9B`）。

## 背景
- 线上出现 `4557.8M` 这类输出：旧实现只到 M，且 M 段在超大值时用 1 位小数，位数随数值增长；`4557.8M` 已 7 列，超出 usage 表格 `reqWidth/cacheWidth = 6` 的惯例（会被截断），卡片 detail 虽还有余量但读数随位数膨胀。
- 实际值示例（旧 → 新）：`839.2M` → `839.2M`；`166.5M` → `166.5M`；`999.96M` → `1B`；`2235.9M` → `2.2B`；`4557.8M` → `4.6B`；`1234567M` → `1.2T`。

## 决策
- **进位链与单位表**：`tokenMagnitudes = [E(1e18), P(1e15), T(1e12), B(1e9), M(1e6, twoDecimalsUpTo=1e8)]`，由大到小；k 段（<1e6，截断到整千、无小数）不属于链。
- **进位规则**：取“最大的、使 `u >= div` 的单位”→ 按该单位精度 `FormatFloat` → `trimTrailingZeros` → 解析回数值；`≥ 1000` 且不是最大单位则 `i--` 继续。判定基于**渲染后的字符串**，因此“四舍五入到 1000”与“本就 ≥1000”同一条路径，用户看到的数就是判定依据。
- **精度**：M 段保留旧行为（`u ≤ 100,000,000` 用 2 位小数：`1.54M` / `50.91M`；之上 1 位：`123.5M` / `938.6M`）；B 及以上恒用 1 位小数（`2.2B`、`4.6B`、`1B`、`1.2T`），理由是进位后的值都远超旧实现已经使用 1 位小数的 100M 分界，风格即“大值 1 位小数”的延续。
- **支持到 E**：任务要求“至少支持到 T”，但 int64 全域要满足“缩放值 < 1000”，只到 T 会让 `int64 max` 长成 `9223372T`；补 P/E 后全域不变式成立（`9223372036854775807` → `9.2E`）。
- **负数**：符号在 `FormatTokens` 外层统一处理（沿用 min int64 安全取绝对值的原写法），进位逻辑只作用在无符号量上。
- **测试**：`numbers_test.go` 表驱动覆盖不进位（`839.2M`/`166.5M`/`999.9M`）、进位（`999960000 → 1B`、`2235.9M → 2.2B`、`4557.8M → 4.6B`）、四舍五入进位（`999.96M → 1B`、`999999999 → 1B`）、跨两级（`999.96B → 1T`、`1.2T`、`999.96T → 1P`、`2P`、`9.2E`）、小值与 k 段不变、负数进位；`planusage/report_test.go` 卡片用例新增 `4_557_800_000 → 总额 4.6B 词元`。

## 被放弃的方案（必填）
- **把 M 段“≤100 单位用 2 位小数”的窗口等比推广到 B/T（→ `2.24B` / `4.56B`）**：与本轮验收示例（`2.2B`、`4.6B`）冲突，且进位后的值全都远在“大值 1 位小数”区间，等比推广反而使有效数字膨胀；否决。
- **数值比较判定进位（`round(scale) >= 1000`）而不解析渲染串**：需为每个单位重复实现一次取整，且与浮点表示差异耦合（如 `float64(999950000)/1e6` 的实际值 ≈ 999.9500000000000455，略大于 999.95，十进制 .95 边界并不精确落在 float64 上），容易与显示值不一致；解析渲染串使“显示什么就按什么的进位”，实现单一；否决。
- **只做 M→B，不加 T/P/E**：`1234567M` 仍是 8 位数，且不满足“单位缩放到数值 <1000”的规则；否决。
- **引入 `go-humanize` 之类的库**：仓库里它只是 indirect 依赖，且其风格（`1.4B`、不同取整）与现实现（尾部去零、整数不带小数点）不一致，会牵动大量既有断言；否决。
- **改 JSON/接口侧数值或字段名**：契约层面不允许，且需求只要求人类可读渲染；否决。

## 已知限制
- **P→E 档进位阈值受 float64 网格影响（M/B/T 档精确）**：对 ≥ 999,949,999,999,999,936 的 64 个 int64 值（1e18 量级 ULP=128，恰为网格点 999,950,000,000,000,000 下方半个 ULP）会提前判进位、渲染 `1E`（精确算术下应为 `999.9P`）；M/B/T 档参与运算的整数与除数均精确可表示，边界行为与「渲染到 1000 即进位」一致。该量级（~1e18 词元）实际不可达；> 2^53 的显示抖动是 float64 表示的固有属性，不建议为此改成整数算术。
