## 一句话结论
- oracle 证伪的 **C4**（卡片与 JSON 不一致 / 数字被截断）按主代理裁定 R1 重做：`formatTokenPair` 不再
  「按总额选单位 + 只拦整数位 > 4，不可读就向上一级重试」，而是**对四档（亿 / 万 / 千 / 原值，无后缀）
  各渲染一次整对，再逐档打分**，五把键按固定顺序比较：`fits`（整对宽度 ≤ `clinePairWidthBudget`
  = 行内指标段的预留列数 `clineNumberWidth`）> `plain`（非零值不得渲染成全零）> `narrow`（两侧各 ≤
  `clinePairSideBudget`，即「预留列 = 侧 + 1（`/`）+ 侧」的分割）> `distance`（离总额的自然档最近）>
  `coarser`（同分取更大单位）。
  **硬规则**：任一阶梯只要有一步装得下（`fits` 是首键），赢家就装得下预留列。第五轮的
  **两趟式后备阶梯**（主阶梯四档都没有 fits 时才启用 亿亿/万亿/亿/万/千/原值 六档，且每档多一个
  「去小数」变体，见下〈第五轮补记〉）把这条的边界推到 **1e18 量级**；该量级里**不只打满对**会超宽
  （哪些形状、哪些 total 由 `TestFormatTokenPairInt64Tail` 的表钉住）。真实窗口的额度量级与 1e18 之间
  的大段由后备阶梯收进预留列内，代价是 `fits` 优先于 `plain`：某些形状会把非零值读成 `0<unit>`
  （即 R1 的「宁舍精度也不许截断」，区间与机制见〈代价〉节）。
  `plain` 排在 `narrow` 之前，因为「非零却渲染成 0」是把数字藏掉（卡片与 `/admin/quota` JSON 不一致，
  即 C4 本体），而 `narrow` 不满足只是读数比理想宽几列（数字仍在，行也不超宽）。
- 裁定里「必须成为用例」的六条形态全部落地为表驱动用例（含一条现状保持与一条 万 → 亿 的翻档），
  期望串见 `TestFormatTokenPairUnitLadderBudget` 的表；先 FAIL 后 PASS 的原文见下〈先 FAIL 后 PASS〉节。
- 新增 `TestFormatTokenPairUnitLadderBudget`（`internal/planusage/report_test.go`）：表驱动 + 一条
  **性质扫描**（总档覆盖各档位边界与 万/亿 边界的密集段；逐对断言「两侧同单位 + 宽度 ≤ 预留列 +
  非零侧不得渲染成全零 + 侧分割**可达时**必须取到」）+ 一条卡片级断言（不得出现 `…`、必须出现翻档后的
  亿 对）。扫描用的总档、占比与批量区间就在测试里，本笔记不复述。
- 文档收尾同时落地：R2 左半口径（`0/池`）、R3 措辞、R4 五处 superseded 注记、R5 遗留清单（本文末节）。

## 背景：oracle 证伪了什么
- 第二轮那版规则（本目录 `20261008-clinepass-attribution-round2-fixes.md` 的 S2 节）是「按总额落档选**一个**
  单位 + 只拦『整数位 > 4』与『非零渲染成全零』，不可读则**向上一级**重试」。它在三类输入上错：
  1. **小池被大单位吃掉**：总额与分子都小于该档单位时，整对渲染成 `0<unit>/0<unit>`（或左右不齐），
     而向上一级重试只会更粗 —— 卡片写 0、JSON 写真实值，正是 C4 的「卡片与 JSON 不一致」。
  2. **边界上仍溢出字段**：总额恰好落在某档的「整数位 + 一位小数」都要写出来的量级时，该档的整对宽度
     超过预留列（旧检查用「整数位 > 4」当「每侧 ≤ 预留侧宽」的代理，带小数点的形态恰好漏过），
     卡片被 `render.Truncate` 截成带 `…` 的读数。
  3. 「不可读就向上一级」只有一个方向：小分子在小总额下往上（更粗）只会更不可读，没有向下的一步可走，
     四档试完只能**回落总额自己的单位**——「非零渲染成全零」这个形态在旧规则里无解；而同一个「每侧 ≤ 侧宽」
     预算又要求超宽时升档，两种诉求在同一输入上会互相指回对方（一个输入同时要求降档与升档），旧规则没有
     仲裁它们的规则。
- 主代理据此把规则改成**有限四档 + 全序打分**（R1）：档位有限 ⇒ 每档只评一次、比较是全序 ⇒ 搜索必然
  终止（没有步进方向互相打架的死循环），且「降一档变精确 / 升一档变宽」两种诉求被同时编码进打分键。

## 改动逐项（R1）
### 阶梯与起点
- `clinePairUnits`（`internal/planusage/report.go`）：亿 / 万 / 千 / **原值 {div: 1, suffix: ""}**。
  原值档是阶梯的**底**（不是起点）：只有上面三档都会把非零值渲染成 `0<unit>` 时才落到它。
- `clinePairUnitStart`：起点 = 总额够得着的最大单位（按档位因子比较）。**起点不含原值档**，这条是
  「保持现状精度观感」的实现（小池仍读带单位的数）。
- `clinePairRawIndex`：原值档下标。

### 打分
- `clinePairCandidate`：一档的整对渲染 + 三个可读性属性（`text` / `fits` / `plain` / `narrow`），
  两侧永远来自**同一档**（不可能出现两侧单位不同、要读者换算的对）。
- `clinePairCandidates(used, total)`：把四档全部渲染出来（生产与测试共用同一份候选构造，测试因此不需要
  重写阶梯）。`clinePairBackupCandidates` 是后备趟的同名物，每档两个变体（一位小数 / 去小数）。
- `(clinePairCandidate).beats`：五键全序比较，键序即规则序（注释里逐条给了理由）。
- `clinePairDistance`：候选档与起点档的档距，用于 `distance` 键。
- `clinePairPlain(text, value)` + `hasNonZeroDigit`：`plain` 的判定 —— 值为 0 时任何档都算 plain
  （`0/池` 是真实读数），非零值渲染出的整串没有非零数字（`0` / `0千` / `0万` / `0亿`，含小数位）即
  not plain；带非零小数位的渲染（格式化器的两位小数兜底）算 plain。
- `formatTokenPair`：**两趟**。第一趟取 `clinePairUnitStart(total)` 作起点，遍历 `clinePairCandidates`，
  用 `beats` 选出唯一赢家；第一趟有 fits 候选就直接返回它（现实量级行为逐字节不变）。第一趟没有任何
  fits 候选时走第二趟：起点 `clinePairBackupStart(total)`、候选 `clinePairBackupCandidates`、
  只接受 fits 的候选，同一套五键选出后备赢家；两条阶梯都没有 fits 时才返回第一趟的赢家。
  两趟都是「固定档位 × 五键全序」⇒ 常数级、必终止。

### 两个预算常量（R1 要求「写死在代码里并注释与 `clineNumberWidth` 的关系」）
- `clineNumberWidth`（行内指标段的列预留，本笔未改）
- `clinePairWidthBudget = clineNumberWidth`：**硬预算**，整对宽度，超了就是会被 `clineRowLine` 的
  `Truncate` 截断。它单独成一个常量，是因为打分发生在**行写出来之前**。
- `clinePairSideBudget`：**偏好预算**，「预留列 = 侧 + 1（`/`）+ 侧」的两侧各多少列（够写四位数 +
  一个宽单位）。它不是硬规则（见「遗留」）。
- 依赖关系：`clineNumberWidth`（行的字段预留）→ `clinePairWidthBudget`（硬）→ `clinePairSideBudget`
  （偏好）。三者都由 `formatTokenPair` 自己的打分保证：真实窗口量级里 `clineRowLine` 的 `Truncate`
  不会碰到数字；但它是**可达的**兜底 —— int64 尾部那些两条阶梯都装不下的对（`TestFormatTokenPairInt64Tail`）
  确实会被它切掉，注释已按此改写（不再写「不可达」）。

### 判定顺序为什么是 fits > plain > narrow > distance > coarser
- `fits` 第一：R1 的硬要求是「任何输入下不许出现被截掉的数字」（R1 把它写在「超宽 → 升一档（更大单位，
  宁舍精度也不许截断）」里），截断 = 数字不可得，比精度问题严重。
- `plain` 第二：非零渲染成 0 是**卡片与 JSON 不一致**（C4 本体）；R1 的调整方向里「非零成 0 → 降一档」
  就是这条，它优先于「超宽 → 升一档」。
- `narrow` 第三：两侧都进侧预算才是字段被设计成的形状，但它只是「更好读」，不该盖过前两条 ——
  小分子配 万 档总额时唯一诚实的档就是原值档（右半必然超侧预算），万 档边界的份额也是反例（见「边界扫描」）。
- `distance` 第四：上面三条并列时，取离总额自然档最近的一档，保住现状观感与精度。
- `coarser` 第五：上面全并列时取更大单位（亿 > 万 > 千 > 原值），即 R1 「超宽 → 升一档」的方向，
  读起来更短更整；这条是**唯一**会牺牲精度的键，也是「升档舍精度」这一既有取舍的落点。它在**档距并列**
  时也生效：某档总额上「更细的档 + 更粗的档」都诚实、都装得下、都每侧 ≤ 侧预算且档距相同时，取更粗的
  那一档（读数由细变粗，见「遗留」的取舍节）。具体档位与读数见 `TestFormatTokenPairUnitLadderBudget`。

### 裁定六条形态的 before / after
裁定指定的六条形态全部成为用例（表驱动），另有两条额外形态。**改前 / 改后 / 期望串一律以测试为准**，
本笔记不复述：`TestFormatTokenPairUnitLadderBudget`（`internal/planusage/report_test.go`）的表驱动部分
逐条断言，卡片级部分断言「不得出现 `…`」与翻档后的 亿 对。形态类别：
- 极小对（分子分母都小）：旧规则被大单位吃掉 → 落到原值档；
- 极小分子 + 小总额：旧规则左右不齐 → 整对落原值档；
- 现状保持两条（起点档即 plain + fits + narrow 的形态）；
- 万 档边界溢出（旧规则写出超宽对、卡片带 `…`）→ 翻档到 亿；
- 「份额 + 边界总额」形态（改前已正确）。

### 边界扫描（R1 的批量断言）
- 测试里给出总档集合（各档位边界点）、两条批量区间（万/亿 边界的密集段与某档的舍入边）与占比集合
  （卡片真实的算式 `used = total × percent / 100`），再加绝对分子形态（`1` / `4` / `total−1` / `total`，
  占比产不出的恶意输入）逐对断言四条性质。档位与区间见 `TestFormatTokenPairUnitLadderBudget`。
- **不变量**（扫描范围内）：两侧同单位；整对宽度 ≤ 预留列（扫描范围内截断不可达；范围外由 int64
  尾部那些两条阶梯都装不下的对占住，`Truncate` 是可达兜底）；`used != 0` 时左半必须有非零数字、
  `total != 0` 时右半必须有非零数字（= 不与 JSON 冲突）。
- **条件性不变量**：四档里**存在**「plain + fits + narrow」的档时，赢家必须 narrow（两侧各 ≤ 侧预算）。
  这条为什么必须带条件：小分子配大单位总额时，万/千/亿 三档都把该分子渲染成 `0<unit>`（不 plain），
  唯一诚实的档是原值档（右半超侧预算）—— 赢家不 narrow，却诚实且装得下；某档的份额形态同理
  （细档超侧预算、粗档把分子读成 0），赢家是**修法前卡片本来就写的那对**（零回退）。
- 扫描上界由「分子 = 1 token 时原值档恰好还装得下」定出；再大就是原值档也超宽，第一趟里只剩粗档装得下、
  而它把 1 token 读成 `0<unit>` ⇒ 「非零侧不得渲染成全零」这条断言在扫描范围外不再成立（键序 `fits`
  优先，见「遗留」）。扫描范围外「整对 ≤ 预留列且无省略号」这一条由第五轮的后备阶梯接管（性质用例见
  〈第五轮补记〉）。

## 被放弃的方案（必填）
- **步进式规则（按方向逐档调整：非零成 0 就降、超宽就升）**：否决。两个方向在同一侧同时成立时没有终止
  规则（升到顶又得降回来），实际实现里必然要偷偷定优先级；改成「有限四档一次评分」后终止性与优先级都
  是显式的（键序），也便于用性质扫描验证。
- **把「每侧 ≤ 侧预算」当硬规则（R1 字面里的「每侧显示列预算」）**：否决。存在输入会让它**振荡**：
  粗档把分子读成 `0<unit>`（非零成 0 → 降一档），细档右半超侧预算（超预算 → 升一档），两边互相指回对方；
  而 R1 同时要求「阶梯有限，必须能终止」。硬预算改挂在**整对预留列**（R1 允许「如预算需要调整要说明理由」：
  理由是上面这条振荡，且硬预算取整对才与 `clineNumberWidth` 一一对应），每侧侧预算降为偏好档；代价是
  万档/原值档偶尔出现超侧预算的侧（整对仍 ≤ 预留列，绝不被截）。
- **新增更细的档（十万 / 千万 / 百亿…）**：否决（与 S2 同理由）。字段只有四位整数位，多一档只多一个要逐档
  验证的边界；打分的 `fits` 已经保证不会溢出。
- **跨档混单位（分子用更细的档、分母用总额档）**：否决。对变成两个不同量纲，读者要自己换算才能比较，
  也破坏「两侧同单位」这条既有契约。
- **把原值档当起点（总额小于最小单位时直出原始数字）**：否决。带单位的读数（`1.3千` 一类）是现状观感与
  R1「起点按总额落到自然档」的要求；原值档只作为兜底。
- **给 `clineRowLine` 的 `Truncate` 加断言/panic（把兜底变成硬失败）**：否决。渲染层不 panic；
  改用「打分保证 + 性质扫描证明」的组合，成本更低且不引入新的崩溃面。

## 第五轮补记（2026-10-08）：后备阶梯 + 溢出防护 [MARK-PRISM-C4FIX2-20261008]

### 为何要补：上一版的「保证」与实测不符
- 上一版把「四档里只要有一档装得下，行内 `Truncate` 就不可达；只有极大的总额才落到它」写成保证。
  实测（verifier/oracle，隔离副本 + 本工作树）不符：主阶梯止于**亿**，而 亿 在自身整数位变多之后
  就超宽，所以「主阶梯都不 fits」的真实起点远早于上一版声称的量级 —— 中段的一大段总额（含某档的
  打满对与「档位因子 × 十」的形态）在主阶梯里都没有 fits 档，卡片行被截。

### 机制：两趟式，第一趟逐字节不变
- 第一趟完全沿用原候选与五键；**只有第一趟没有任何 fits 候选时**才启用后备趟。
- 后备阶梯 `clinePairBackupUnits` = 亿亿 / 万亿 / 亿 / 万 / 千 / 原值，即主阶梯用同一个档位因子继续
  往上（亿 → 万亿 → 亿亿）；每档渲染**两个变体**：同单位一位小数（`render.FormatTokensUnit`）与
  **去小数（整数）**（`clinePairWholeText`）。
- 后备趟只接受 `fits` 的候选，键序仍是 fits > plain > narrow > distance > coarser；两条阶梯都没有 fits 时
  返回第一趟的赢家（不改变「宁舍精度也不许截断」的取向，只是把它的触发点推到 1e18 量级）。
- 任务书建议只加「万亿」一档；实测**不够**：继续往上到 亿亿 的那两档的打满对仍超预留列。所以按同一
  档位因子补到 亿亿（不引入混单位、指数记法或新记号，两侧仍永远同一档）。

### 代价（有意接受，不是缺陷）
- **打满对读成 `0亿亿` 的区间**：该段没有**同单位**且诚实又能装下的档（细档的整对超宽、粗档的小数形态
  也超宽），唯一装得下的是 亿亿 档的整数变体（小数被舍成 0）。产物是**两侧都读成 `0亿亿`**，比改前的
  「诚实但被截」信息更少。机制就是 `fits` 首键：更诚实但更宽的候选被 fits 的粗档全零变体淘汰 ——
  与「极小分子读成 `0<unit>`」同源（`fits` 是首键、预留列是硬预算）。
- **极小分子读成全零是按块发生的**：不是单一起点，而是每个「亿 半的整数位 + 小数位」周期内重复的块，
  块内还有前一点落在预留列内但不诚实的 `0亿/…亿`。块起点与块宽见 `TestFormatTokenPairInt64Tail` 的常量
  与扫描。机制同上。JSON 侧数值不变（`limit_tokens_estimate` / `measured_tokens` 仍是精确 int64）。
  真实窗口的额度量级产不出该段。若以后判定「宁可截断也不能读成 0」，需把 `fits` 与 `plain`
  的优先级或硬预算重新裁定。
- `plain` 是**整对**的合取：分母被藏与分子被藏同分，所以「只有唯一 fits 候选」的输入不会因为
  「至少别把总量藏掉」而改选，本轮的键序（`fits` 最优先）也不允许它改选。

### 同轮的第二项：`reversePool` 溢出防护（`internal/planusage/estimate.go`）
- `reversePool` 用 float64 除法再转 int64：商超出 int64 范围（大数 ÷ 接近 1e-19 的份额）或为 NaN 时，
  转换结果在 amd64 上是**负值** —— 卡片会写出「负数池」。
- 现行：NaN / 商 < 0 返回 0；商 ≥ float64(math.MaxInt64) 饱和到 `math.MaxInt64`（**没有**任何人为池上限）。
  防护**只保证不返回负值、溢出饱和**，不保证精度：商走 float64 除法后又加了 0.5 再转 int64，所以误差
  从 **float64 整数网格下界之上不远处**就开始 —— 加 0.5 会落在两个 float64 值之间、舍到偶数，
  于是池比真值大 1，尽管那个计数本身可表示；量级越大量化步长越大。边界与量化步长由
  `TestReversePoolNeverWraps`（`estimate_test.go`）的用例钉住。回归用例先 FAIL 后 PASS。
- `internal/render/numbers.go` 只补注释：`FormatTokensUnit` 的 float64 缩放让 int64 顶值渲染成与真值
  差一个亚单位小数的字符串（两次取整方向相反，显示层取整，JSON 不变）。

### 本轮用例
- `TestFormatTokenPairBackupLadder`（`report_test.go`）：表驱动钉住各档读数 + 性质循环（各量级 ×
  {极小分子、4、total/10、total/2、total−1、total}：宽度 ≤ 预留列、无 `…`、两侧同单位、同输入两次同值）
  + 档边界邻域（四种形态无 A-B-A；`total−1` 形态的单点尖峰另测：遍历各块，断言每块恰有一个预留列宽的
  单点尖峰、两侧回到更窄且相等的对，并把落点计入两个计数常量）。尖峰的形状、k 范围与计数常量一律以
  测试的断言与常量为准，本笔记不复述。
- `TestFormatTokenPairUnitLadderBudget` 的「扫描范围外」段改为对**两条阶梯**判 `fitsReachable`（原来只看主阶梯，
  会把后备阶梯能装下的形状误判成「没有 fits 档还读成 0」）。旧断言一行未删，只把 fits 的判定范围并入后备阶梯。
- 既有小池断言全数保持。
