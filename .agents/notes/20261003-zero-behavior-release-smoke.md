# 零行为版本的发布冒烟：部署前抓基线 → 部署后同命令再抓 → 同一归一化脚本机械 diff

## 一句话结论
- **行为不变的版本（如 v0.36.4：仅测试侧 + 测试可观测性）也必须冒烟**，但冒烟的形态不是「看一遍有没有正常」，而是：**部署前在线实例抓基线 → 部署后同命令再抓一份 → 用同一个归一化脚本做机械 diff**。肉眼核对等于没冒烟——人眼看不见字段顺序、看不见 JSON 里多一个键、也记不住五份输出里哪个数字上次是多少。
- 归一化脚本预先声明一份**豁免字段清单**（会自然变化的值）与一份**不豁免清单**（契约内容），diff 只报后者；凡是 diff 之外的东西，要么进豁免清单并写清为什么豁免，要么改成**独立结构断言**在原始抓取上判定，**不得**用肉眼补位。
- 发布顺序必须把 **push 放在最后**（tag 先打、门禁先跑、部署成功后最后才 push），使任何一步失败时远端仍停在上一版，回滚只动本地。**任何情况都不 force push。**

## 背景
- v0.36.4（cache flake 真 join 栅栏修复，释放提交 `188b7f4`，tag `v0.36.4`，HEAD 与 `origin/main` 均一致，线上已部署）的 README/Changelog 明确声明「程序化接口与人眼可见输出（quota 卡片宽度与间距、`?format=table`、`--json`、`/admin/quota` JSON、`/metrics`、CLI flag）逐字未动，二进制行为与 v0.36.3 一致」。这类「零行为」版本最容易出现的发布事故不是新 bug，而是**没人能证明它真的零行为**：只跑 `go test` 证明的是代码没回归，证明不了「线上这一份二进制与上一版对外表现一致」。
- 双审在 v0.36.4 发布后提出收口项，其中一条是把「零行为版本的发布冒烟」本身定成方法并留痕：此法在 v0.36.3→v0.36.4 这一轮已经实际用过（五份抓取 + 机械 diff + 一组结构断言），但此前只散落在过程里，没有成文的边界约定（哪些值必须豁免、哪些不许豁免、盲区怎么补、失败了怎么回滚、提交怎么拆）。本篇把这套做法与它的边界定案。
- 之所以强调「**基线必须用部署前的在线实例**抓」：本地 `go run`/自签端口抓的「基线」与线上实例的配置、账号 roster、SQLite 里的历史用量都不同，diff 出来的差异全是环境噪声，反而掩盖真正的行为差异。

## 决策
- **冒烟 = 两份抓取 + 一次机械 diff，缺一不可**：
  1. **部署前**：对当前在线的旧版本实例抓基线（此时新二进制可能已 `install`，但进程仍是旧 inode，或干脆未开始部署）。
  2. **部署后**：`deploy.sh` 走完、健康验证通过后，用**完全相同的命令**再抓一份。
  3. 两份喂给**同一个归一化脚本**做 diff。脚本本身与抓取命令一起版本化（同一套参数、同一份豁免清单），不能「部署前用 A、部署后用 B」。
- **五份抓取**（覆盖人眼可见输出与程序化接口两面）：
  - quota 卡片：`prism quota --no-color`（人眼可见的卡片文本）；
  - legacy 表格：`?format=table`；
  - `--json`：`prism quota --json`（CLI 侧 JSON 契约）；
  - `/admin/quota` JSON：`curl .../admin/quota`（HTTP 侧 JSON 契约）；
  - `/metrics`：`curl .../metrics`（字段名集合与类型契约）。
  - 每份都同时带**退出码**与 **HTTP 状态码**（见豁免清单——状态码本身豁免，但「端点是否 200」作为结构断言单独判定）。
- **同一脚本、同一环境变量**：`COLUMNS` / `LINES` / `TERM` / `NO_COLOR` / `LANG` 固定成同一组显式值再抓。卡片宽度虽由 `cardWidth` 推导、不读终端宽度，但抓取环境不一致会让归一化脚本拿到不同形状的输入（折行、有无转义序列），把环境噪声当成行为差异。
- **归一化豁免字段清单（以及为什么豁免）**：
  - **时间戳 / 时区**（`FetchedAt`、`UpdatedAt`、日志与 metrics 里的时间）：版本不改变时间的前进，diff 必然全行不同。
  - **进程运行态**（pid、启动时间、uptime、systemd 状态里的时间戳）：进程重启即变，与二进制行为无关。
  - **数值型运行量**：`/metrics` 的全部计数器与耗时（expvar 计数随请求累加，重启后归零或跳变）、JSON 里的数值叶子、卡片/表格里的百分比·倒计时·限额估算·token 总量：这些字段的**存在性、类型、字段名**是契约，但**取值**由流量与时钟决定，部署前后不同是正常的。
  - **由数值派生的格式单元**：同一个倒计时量级不同形状就不同（`2m` / `3h 09m` / `4h 55m` / `6d 18h`），是数值的字符串投影，豁免方式与数值本身相同。
  - **对齐填充宽度**：把 **2 个以上连续空格折叠为 1**。卡片行按 `DisplayWidth` 右对齐/行尾补齐（v0.36.3 起改为行尾 fill），数值长短一变填充就变；这一条同时是**既存盲区的成因**（见下）。
  - **HTTP 状态码行**：如 `200`；但「端点是否 200」改由结构断言在原始抓取上判定，等于把它从豁免提升为**单独守护**。
  - **`/admin/quota` 顶层 `providers` 数组顺序**：源码 `internal/planusage/cache.go` 的 `Cache.List()` 是 `for _, s := range c.items { out = append(out, s) }`——**直接遍历 Go map**，同一进程连续请求的顺序就不同，**从来不是契约**。本次实拍证据：同一进程连打 5 次得到 4 种顺序。人眼可见的展示序不受影响（`RenderCards` / `RenderTableAt` 走 `accountSortKey`，即 Gemini → SuperGrok → ClinePass），由结构断言守护（见盲区一节）。
- **不豁免（变了必须报出）**：
  - **文案**（卡片的中英文文本、legacy 表格的列格式文本、错误码中文化映射后的展示串）；
  - **分隔符与边框字符**（`╭─` / `│` / `├─` / `╰─` 与 dash 填充形态）；
  - **模块顺序与行数**（卡片里「标题行 / 数据行 / note 行 / 边框行」的排列与条数）；
  - **JSON 键与结构**（`--json` 与 `/admin/quota` 的键名、嵌套层级、数组形状、字段类型）；
  - **`/metrics` 的字段名集合**（只豁免取值，不豁免「多了/少了一个字段名」）。
- **已知盲区（必须写在方法里，不许假装 diff 覆盖了一切）**：
  - **进度条格数（23）与派生的填充宽度不被 diff 守护**：填充宽度被上面「2+ 连续空格折叠为 1」豁免掉了，进度条格数本身也没有进 diff 的比对对象——两者恰好是同一类「塌在归一化里」的几何事实。若一次改动把 23 格改成 20 格、或把行宽从 58 改成 56，归一化 diff 可能完全安静。
  - 因此改用**独立结构断言**在**原始抓取**（未归一化）上判定，本轮的断言集：
    - 每行显示宽度恒 **58**；
    - 进度条恒 **23 格**；
    - 进度条起始列（其前恒 14 列）；
    - 名字列宽（`clineNameColMin = 9` 下限，长名不截断）；
    - 模块间距恒 **1 空格**；
    - provider 展示序恒 **Gemini → SuperGrok → ClinePass**；
    - 卡片里无「后重置」文案（v0.36.2 已去掉，不得回归）；
    - 表头与窗口序（`5小时限额` / `周限额` / `月限额`，短→长）；
    - 五个端点均 **200**；
    - `--json` / `/admin/quota` / `/metrics` 的**字段路径集合与类型**与基线一致（只定性、不定值）。
  - 这组断言与归一化 diff 是**互补关系**，不是替代关系：assert 负责「形状没塌」，diff 负责「内容没变」。只做前者会漏掉同形状下的文案/字段变化，只做后者会漏掉几何塌陷。
- **回滚预案（两支，不得混写）**：
  - **① 未推送**（`push` 被刻意放在最后，绝大多数失败落在这一支）：`git tag -d <tag>` → `git reset --hard <部署前提交>` → 用旧版二进制重新跑 `deploy.sh`。此时远端仍在上一版，本地三连即可完全回到发布前状态。
  - **② 已推送**：本地 `git tag -d` / `git reset` **修不了远端**——tag 与提交已经在 origin 上，只能 `git revert <释放提交>`（或 revert 对应 fix 提交）并正常推送，再按①用旧版重新部署。**任何情况都不 force push**：force push 会改写他人已拉取的历史，比一次失败发布严重得多。
- **提交拆分约定**：
  - 实现/修复提交与 `chore(release): vX.Y.Z` **分开**；修复提交过一遍门禁，释放提交只做 README + tag。
  - **README（版头 + Changelog）只进释放提交**，不进实现提交——否则实现提交里就带着「对外可见的版本说明」，一旦实现提交被 revert，版本说明与代码就对不上。
  - **tag 打在释放提交上**，与仓库既有 `v0.36.0`–`v0.36.4` 一致，全部是**轻量 tag**（`git tag vX.Y.Z`，无 `-a/-m/-s`）。
  - **打 tag 前再跑一次全量门禁**（`go build ./...`、`go vet ./...`、`go test -count=1 ./...`、`for s in scripts/test_*.sh; do bash "$s"; done`、`python3 scripts/test_generate_mcp_tools.py`），确保被 tag 的正是被验证过的那棵树。
  - `deploy.sh` 只做机械部署、**不做 git**（commit message / Changelog / tag 号由调用方判断），因此「push 放最后」必须由发布流程自觉保证，脚本不会替你把 push 挡在门外。

## 被放弃的方案（必填）
- **① 只看 `go test` 全绿 + `deploy.sh` 的 `/ready` 健康验证**：`go test` 证明的是代码没回归（suite 时间点的那个世界），`deploy.sh` 的 `/ready` 只证明「进程起来了且至少一个账号 healthy」。**没有任何一条能证明「对外表现与上一版一致」**——零行为版本的恰是这条没人管。否决。
- **② 肉眼核对五份输出**：五份输出里有数百个会自然变化的值，人眼既记不住也看不出字段顺序、JSON 键增减；且没有可复现的判定记录，事后无法证明「当时确实核对过」。否决（这正是本篇「肉眼核对等于没冒烟」的由来）。
- **③ 把 diff 的对象扩大到全部原始输出、不做归一化**：等于豁免清单为空，diff 会被时间戳/pid/计数器淹没，必然巨量假阳性；人在假阳性里挑真差异的行为模式，回到②。否决。
- **④ 归一化时连空白一起保留、只豁免时间戳与 pid**：进度条格数、卡宽、模块间距这类**几何事实**正是靠空白表达的，保留空白意味着任何一次数值长度变化都让整份输出 diff 失败——但它同时保住了守护几何的能力。本篇取的是**折中**：豁免填充宽度（接受 diff 不守护几何），**另建结构断言**补齐，而不是假装某一边能同时做到。否决「单靠 diff」的思路。
- **⑤ 只做基线一遍、部署后不复抓**（或用部署后的输出反过来当基线）：两份都相同就没有 diff 可言；「事后补的基线」无法区分「版本引入的差异」与「环境自身的变化」。否决。

## 遗留（未决 / 需后续处理）
- **归一化脚本与抓取脚本尚未入库版本化**：本轮的抓取与归一化是过程性执行的，脚本本身与豁免清单还没有作为仓库资产固化（附断言集脚本同理）。若下次零行为版本仍靠「临场重写一遍」，参数漂移会重新引入假阳性/假阴性。建议把 `smoke_*.sh`（抓取 + 归一化 + diff + 断言）收进 `scripts/`，并在 `AGENTS.md` 的发版流程里点名；**待用户决策**，本笔未动（本笔允许改动范围仅四处，且不含 `scripts/`）。
- **零行为版本的「豁免清单」是每版重审的**：本清单按 v0.36.4 的五份抓取形态定案；若后续版本新增/重命名字段、或卡片几何再变（宽 58/61、进度条 23 格等），清单与断言集要同步重审，不能照抄。特别是「`/admin/quota` 顶层 `providers` 数组顺序」这条豁免**依赖 `Cache.List()` 继续直接遍历 Go map**——若哪天给它加了稳定排序，这条豁免应改成「必须排序」的**不豁免**项。
- **五份抓取未覆盖所有端点**：本轮只取 quota 相关五份；`/admin/usage/summary`（含 legacy `?format=table`）与 `/v1/models` 缓存路径未进冒烟集。零行为版本的可信度因此限于这五面，**不是全端点证明**。后续是否扩集**待用户决策**。
- **与 `20261003-cache-flake-join-fence.md` 遗留项的交叉**：该笔记记录的 `internal/util` 固定 `/tmp/prism-debug` 路径并发互踩，最早是在并发跑套件的收尾过程中暴露的；本批（同一收尾小批）已按该笔记给出的方向用 `t.Setenv("TMPDIR", t.TempDir())` 修掉，该遗留项随之关闭——关闭声明以该批留痕为准，本笔记不改写旧笔记正文。
